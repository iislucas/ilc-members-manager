Authentication & Sign-in

How members sign in: the one component that implements it, what the flow decides at each step, and — the part most likely to surprise you — what the browser remembers between visits, and when.

One component, everywhere

There is a single sign-in implementation: InlineAuthComponent in src/app/inline-auth/inline-auth.component.ts. Transient state that outlives a single page lives in SignInFlowService. The server-side lookup is the checkEmailStatus callable, whose result type CheckEmailStatusResult is defined in functions/src/data-model/system.ts.

🔑 The login page /login
LoginComponent is a thin wrapper — its template is one element. It sets showNoMemberOption to true.
🛒 Five purchase flows Step 1
Become a Member, Next Grading, Class Video Library, Instructor License, School License — each embeds it as the first step. showNoMemberOption defaults to false.

That single input is the only difference between the two uses:

showNoMemberOptionAn email matching no membership record…
true login page reaches a dead-end step offering "Become a Member" and "create an account without a membership".
false purchase pages is offered account creation directly. On a purchase page that prompt would be circular — those pages are already where an account gets created.
The same lookup routes differently per page

Whenever a step is derived it is derived from the status plus the page's own policy, never copied from another page's decision. This matters when an attempt is carried between pages.

The steps

InlineAuthStep is the state machine:

StepShown when
EmailNothing known yet; the user types an address.
CheckingcheckEmailStatus is in flight.
GoogleSigninGoogle is the route for this address.
PasswordLoginA password is the route for this address.
CreateAccountNo auth account exists; one will be made.
GuestCreateAccountCreating an account with no membership behind it.
NoMemberLogin page only; nothing matched this address.

Two states pre-empt the machine entirely: if the user is signed in, the signed-in badge and Log Out action render instead; if the address is unverified, the "verify your email" panel renders instead.

Which provider is offered first

stepForStatus decides, in this order:

Routing a looked-up email
  1. hasGoogleProvider → Google. One click beats recalling a password.
  2. hasPasswordProvider → password. Confirmed password, no Google linked.
  3. Neither flag known → fall back to isGoogleManaged.
The trap in the third field

isGoogleManaged is true for any gmail.com / googlemail.com address, not only for accounts with Google actually linked. If it outranked the provider list, a gmail address whose account has nothing but a password would be sent to a Google sign-in that cannot work. It is therefore only a last-resort hint.

Switching provider

Both routes are plain buttons — a primary and a secondary — not a hidden menu:

StepPrimarySecondary
PasswordLogin Sign In Sign in with Google — only if canUseGoogle()
GoogleSignin Sign in / Sign up with Google Use / Set a password — always
The asymmetry is deliberate

Google is not offered indiscriminately: if an address uses an unmanaged third-party domain (e.g., Yahoo, Outlook) and has no existing Google credential, the secondary Google button is omitted. For addresses with a known Google provider or Google-managed domains (Gmail, Google Workspace via DNS MX check), Google is offered. Even if the account only has a password today, clicking Google will initiate seamless account linking rather than hitting a dead end (see Account Linking & Credential Conflicts). A password is always an available route — the account has one, one can be created, or one can be reset as a recovery path for someone locked out of their Google account.

Account linking & credential conflicts

When a member who originally set up their account with an email and password attempts to sign in with Google (using the same email address), Firebase Authentication throws auth/account-exists-with-different-credential because the project enforces the standard "One account per email address" policy.

Rather than displaying an unhelpful error or creating a duplicate account, the application catches this error and guides the user through a seamless credential linking flow:

Google sign-in credential conflict & linking flow
  1. Conflict Interception: In FirebaseStateService.loginWithGoogle(), the error auth/account-exists-with-different-credential is caught and GoogleAuthProvider.credentialFromError(error) extracts the pending Google credential.
  2. Contextual Notice: InlineAuthComponent stores the credential in the pendingGoogleCredential signal and switches step to InlineAuthStep.PasswordLogin. An informational notice explains:

    An account already exists for you@example.com using a password. Enter your password once to connect Google Sign-In.

  3. Primary Action ("Sign In & Connect Google"): The submit button updates to "Sign In & Connect Google". Clicking it invokes FirebaseStateService.loginWithEmailAndLink(), which authenticates via signInWithEmailAndPassword and immediately executes linkWithCredential(userCredential.user, pendingCredential).
  4. Remembered Preference: Upon successful authentication and linking, rememberSuccessfulLogin('google') writes to persistent localStorage. On future visits, this browser defaults to one-click Google Sign-In, while the password remains fully functional as a fallback.
  5. Cancellation: If the user decides not to link Google, a secondary "Cancel connecting Google" action clears pendingGoogleCredential and restores the standard single-provider password login view.

Wording

Labels and progress messages both follow hasKnownAuthAccount(), so a button and the spinner that follows it can never contradict each other:

SituationButtonWhile in flight
Google, account existsSign in with GoogleSigning in with Google…
Google, no accountSign up with GoogleCreating your account with Google…
Password, account existsSign InSigning in…
Password, no accountCreate AccountCreating your account…

The progress message comes from a pendingAuth signal each auth method sets and clears, rather than being inferred from the current step, which can be stale by the time the request lands. When the service reports LoggingIn without the component having started anything — a session being restored on page load — the message falls back to "Signing in…".

Changing the email

Past the first step the address renders as a button (#change-email-btn), not a caption. Tapping it returns to email entry with the address kept, so a typo can be corrected rather than retyped, and discards everything derived from it: the lookup result, any remembered login, and any attempt in progress.

It used to be a dead end

The address previously rendered as an inert <div> styled to look like a field, and the only way to change it was a "Use a different email" item buried in an overflow menu.

What the browser remembers

This is the part with the sharpest rules, because getting it wrong leaks one person's email address to the next person at the same computer.

RememberedLogin — persistent, post-authentication only

Stored in localStorage under ilc-remembered-login:

type RememberedLogin = {
  email: string;
  method: 'password' | 'google';  // the provider that actually worked
  canUseGoogle: boolean;          // whether Google was available when last checked
};

The rules that make it trustworthy:

  • Written only after a sign-in succeeds — never when an email is merely looked up. Every field therefore records something observed, so nothing has to be guessed when it is read back.
  • Cleared on logout, along with the email field. Signed out means empty.
  • Cleared when the user changes the email.
  • Validated on read. Anything not written by the current code — malformed JSON, a missing email, an unrecognised method — is discarded rather than half-trusted. The cost is one extra email entry.

On restore the flow resumes at PasswordLogin or GoogleSignin per method. emailStatus stays null, because no lookup has run this visit; hasKnownAuthAccount() is still true, since an account was used here before.

History — the bug this replaced

An earlier version cached the email inside checkEmail(), i.e. as soon as Continue was pressed, and rebuilt a full CheckEmailStatusResult from it with hasMemberRecord: true hardcoded. That pinned typos permanently, survived logout, and made the create-account step claim a membership record that had never been checked. The old key ilc-login-info is actively deleted on init wherever it lingers.

Attempts in progress

SignInFlowService holds the attempt in progress: the email entered and the lookup for it. Someone who types their address on the login page, is told there is no membership for it, and follows "Become a Member" has already answered the question the next page would otherwise ask again.

Carrying an attempt across a navigation

It is deliberately not persisted:

  • it survives an in-app navigation — RoutingService.navigateTo uses history.pushState, so the root injector is not rebuilt — and nothing more;
  • a reload or a new tab starts clean;
  • nothing is written to storage, so this does not reintroduce the pre-authentication caching described above.

It is cleared when the user changes the email and on logout.

Precedence

An attempt in progress reflects what the user just did, so it is adopted ahead of a login remembered from an earlier visit.

Why this runs in ngOnInit, not the constructor

The opening step depends on showNoMemberOption, and Angular does not set inputs until after construction. Deriving it in the constructor would read the input's false default and send the login page to Create Account instead of its no-member guidance.

Tests

inline-auth.component.spec.ts covers this against the in-memory mock from createFirebaseStateServiceMock(), grouped by concern: startup and malformed storage, lookup routing, what may be remembered and when, logout, changing the email, carrying an attempt between pages, provider switching, Google account linking on credential conflict, progress wording, errors, and the no-member dead end.

Two habits worth keeping when adding to it:

Carrying between pages
Simulated by creating a second component against the same TestBed injector — a fresh component, the same root-provided service.
In-flight UI
Progress messages are inspected by holding the auth call open with an unresolved promise, rendering, then releasing it. A test that simply awaits the call can never see the message.

login.spec.ts only checks that the page renders the shared flow with showNoMemberOption on; everything else belongs to the component's own spec.
