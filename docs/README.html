ILC Members Portal Architecture

The official web platform and member portal for the international Zhong Xin Dao I Liq Chuan martial arts community. A high-performance, real-time Progressive Web App (PWA) managing memberships, international gradings, certified schools, instructor profiles, workshop events, Video-on-Demand (VOD) streaming, and unified multi-channel store orders.

🌐 Practitioners & Members Self-Service

Digital passbook tracking student grades, membership status, seminar signups, event proposals, notifications, and subscription renewals.

🥋 Instructors & Schools Community

Student roster management, grading requests acceptance and evaluations, school listings, class schedules, and teaching materials uploads.

🛡️ Headquarters (HQ) Admin Global Control

Unified control plane for global member records, manual order reconciliation, Stripe product syncing, VOD transcoding curation, and backups.

User Roles & Access Control Matrix

The system uses an explicit Role-Based Access Control (RBAC) model cached in Firestore /acl/{email} and evaluated in Firestore Security Rules. This table is the summary; Security Rules & ACL covers how the rules actually evaluate it, and Public vs Gated Views covers what the client does or does not enforce.

Security Rules & ACL

Authorization lives in two rule files — firestore.rules (368 lines) and storage.rules (186 lines). Both deny everything by default and both answer every question by reading one document: /acl/{email}.

These rules are the only real boundary

The Angular app hides controls a user cannot use, but it does not guard routes by role — an admin URL entered by a non-admin renders, and then every read it attempts fails. Client-side gating is a usability feature; these rules are the security. See Public vs Gated Views.

The ACL document is the index

Rules cannot run queries, and each get() costs a document read against a hard per-request limit. So rather than walking from a user to their memberships, schools and instructor records at evaluation time, Cloud Function triggers denormalise those answers into /acl/{email} ahead of time. Nearly every rule is then a single lookup plus an array membership test.

ACL fieldTypeAnswers the question
isAdminbooleanIs this an HQ administrator?
memberDocIdsstring[]Which member documents is this login linked to?
instructorIdsstring[]Which instructor identities does it hold?
schoolDocIdsstring[]Which schools does it own or manage?
notYetLinkedToMemberbooleanIs this a bare account with no membership behind it?
membershipExpiresstring"life", "YYYY-MM-DD", or empty — used by Storage only.
instructorLicenseExpiresstringSame encoding, for instructor resources.
schoolLicenseExpiresstringSame encoding; the latest expiry across all schools managed.
Why expiry dates are strings

Storage rules have no date type to compare against, so expiry is stored as a sortable YYYY-MM-DD string and compared lexicographically with a todayStr() helper built from request.time. Lifetime membership is the literal "life", which works because 'l' > '9' in ASCII — so it compares as later than any real date. Empty or missing means no access.

Firestore: five recurring patterns

The first match in the file refuses everything; every later rule is an explicit grant.

match /{document=**} {
  allow read, write: if false;
}

A collection with no rule of its own is therefore unreachable from any client, including for admins. Server code uses the Admin SDK, which bypasses rules entirely — that is why collections written only by Cloud Functions (/orders, /instructors, the mirrored subcollections) can be allow write: if false and still be written.

Ownership is checked two ways, because a member document can be reached either by the email on it or by the ACL link: 

function isOwner() {
  return (request.auth.token.email in resource.data.emails) ||
         (memberDocId in getUserMemberDocIds());
}

The same pair appears in each subcollection (/orders, /notifications, /videoGrants, /uploads, /pushSubscriptions, /videoProgress), where the parent member document has to be fetched to read its emails array.

Where a user may edit their own document, the rule pins down which fields — so a member can change their address but not their membership expiry, level or member ID. 

allow update: if hasValidEditUpdate() && isOwner() &&
  request.resource.data.diff(resource.data).affectedKeys().hasOnly(
    ['lastUpdated', 'name', 'phone', 'address', 'city', 'country',
     'emails', 'gender', 'dateOfBirth', 'notificationSettings', /* … */]);

hasValidEditUpdate() additionally requires request.resource.data.lastUpdated == request.time, so every accepted write carries a server-stamped timestamp rather than one the client chose. The same whitelist-plus-timestamp pattern guards /schools and /gradings.

Some access is not cached in the ACL, because it must follow a relationship that can change. Event-manager access to a grading is read live from the linked event: 

function isGradingEventManager() {
  let eventDocId = resource.data.get('gradingEventDocId', '');
  let eventPath = /databases/$(database)/documents/events/$(eventDocId);
  return eventDocId != '' && exists(eventPath) && (
    get(eventPath).data.ownerDocId in getUserMemberDocIds() ||
    getUserMemberDocIds().hasAny(get(eventPath).data.get('managerDocIds', []))
  );
}

Unlinking the grading from the event therefore revokes access immediately, with no trigger to run. Note the eventDocId != '' guard before exists(): it keeps the extra document read off the common path where no event is linked.

Gradings change hands partway through their workflow. Before a manager accepts, the student owns the request and the linked event; after acceptance the event belongs to the grading manager and the student's whitelist shrinks. 

function gradingIsAccepted() {
  let status = resource.data.status;
  return status == 'awaiting-instructor-grading' || status == 'passed' ||
         status == 'not-passed' || status == 'in-review';
}

This is expressed as two separate allow update rules for the student — one gated on !gradingIsAccepted() including the event fields, one gated on gradingIsAccepted() without them. Firestore ORs all matching allow rules, so writing them as alternatives is the idiom for "different permissions in different states". See docs/gradings.md.

Public vs Gated Views

One set in app.config.ts decides which routes render without a login, and one ladder of conditions in app.html decides what a visitor sees instead when they are not entitled to a page.

Gating is UX, not security

There is no role guard on any route. A non-admin who types an admin URL gets the admin component, which then fails every read it attempts because the security rules reject them. The admin section is merely hidden from the navigation menu. Treat everything in this section as "what the user is shown", never as "what the user is prevented from reaching".

PUBLIC_VIEWS

PUBLIC_VIEWS in src/app/app.config.ts is the single source of truth for routes that render without authentication. It currently holds 19 views in three groups:

Directory & calendars
FindAnInstructor, InstructorView, FindSchool, SchoolView, EventsCalendar, EventView, ClassCalendarView, SchoolCalendarView
Catalog & resources
Videos, VideoView, ClassVideoLibrary, Products, DownloadResource, OrderComplete
Purchase flows
BecomeAMember, NextGrading, InstructorLicensePurchase, SchoolLicensePurchase, ClassVideoLibraryPurchase
Why the purchase flows are public

You cannot require a login to reach the page whose job is to create your account. Each of these five pages embeds <app-inline-auth> as step 1 and signs the visitor in on the spot — so the page works signed out, signed in, or halfway through. See Guided Purchase Flows and Authentication.

The rendering ladder

app.html tests these conditions in order and renders the first that matches. Order is the whole design: a public page is resolved before auth is consulted, which is why a visitor never sees a login flash on a public route.

Which branch renders
#ConditionRendersWhy it sits here
1isNotFound()<app-not-found> An unmatched URL is not an auth problem, so it is answered before anything else.
2isPublicPage()The view itself Rendered regardless of auth or data-loading state. This one block replaced duplicate public cases in both the logged-in and logged-out branches, which used to cause a visible re-load flash on auto-login.
3No userSign-in prompt Two variants — see below.
4loadingState() !== LoadedSpinner Signed in, but member data has not arrived; components below assume it.
5incompleteProfile()<app-complete-profile> A soft wall: finish the profile before using member features.
6—Member and admin views One @switch, no role branch. Admin protection is the rules layer.

Two flavours of "please sign in"

Step 3 splits on isLoginPage(), which is true for Views.Login and Views.Home — the root path doubles as the signed-out landing page:

  • Landing — the sign-in box beside a welcome blurb and discovery cards for the public areas. No URL rewrite happens; / stays /.
  • Interception — "This page requires you to be logged in", the same sign-in box, and links to other pages the visitor might have wanted.

Both render the same <app-login>, which is itself a thin wrapper around the shared <app-inline-auth> flow.

Returning to where you were

Views.Login carries an ephemeral returnUrl URL parameter. An effect in app.ts watches login status and, once signed in, navigates to returnUrl if present and Home otherwise.

Why returnUrl is not cleared

Clearing the signal inside the effect would re-trigger the effect before the navigation completed, falling through to the Home redirect and dropping the user's destination. It is left to be overwritten naturally the next time the login route is visited — the reasoning is recorded in a comment at the redirect.

Stripe & Order Fulfillment

Money is never taken by this app. A callable creates a Stripe Checkout Session, Stripe hosts the payment, and a signed webhook tells us what happened — at which point fulfillment turns a payment into membership, a licence, a grading, or video access.

This is the orientation; the reference is elsewhere

Schemas, the subscription state machine, expiry and auto-renew semantics, and the self-service journeys are documented in depth in Orders & Subscriptions (sections 4–13). This section covers how the pieces fit together and where each one lives.

End-to-end

From button press to entitlement

The four moving parts

FileEntry pointResponsibility
functions/src/stripe-checkout.ts createStripeCheckoutSession, getStripeCheckoutSession Builds the Checkout Session, stamping orderType and memberDocId into metadata. The second callable lets the return page show a confirmation before the webhook has necessarily landed.
functions/src/stripe-webhook.ts stripeWebhook Verifies the signature, normalises the Stripe object into a StripeOrder, and dispatches. Unknown event types are acknowledged so Stripe stops retrying them.
functions/src/stripe-fulfillment.ts fulfillStripeOrder The business end: resolve the member, categorise what was bought, extend the right expiry date, create gradings or video grants, and mirror the order.
functions/src/stripe-subscriptions.ts cancelSubscriptionRenewal, resumeSubscriptionRenewal, createCustomerPortalSession Member self-service over an existing subscription.

Webhook events handled

EventAction
checkout.session.completedhandleCheckoutSession — the main purchase path
checkout.session.async_payment_succeeded

Failures must return 500

The handler deliberately returns 500 when fulfillment throws, so Stripe retries with backoff. Swallowing the error and returning 200 would lose the payment's effect permanently — the money is taken but the membership never arrives. Signature verification failures return 400, because retrying those cannot help.

Finding the member

A payment carries whatever identity Stripe happened to have. resolveMemberForStripeOrder tries four routes in descending order of reliability:

  1. metadata.memberDocId or clientReferenceId — set by our own checkout callable, so exact.
  2. stripeCustomerId matched against members.
  3. The customer email looked up in /acl/{email}, taking its first memberDocIds entry.
  4. The customer email matched against the emails array on members.

Returning null is a real outcome — payments do arrive from outside the app — and the order is still recorded for an admin to reconcile.

Deciding what was bought

categorizeLineItem checks orderMetadata.orderType first, and only falls back to substring matching on the line-item description and product ID: 

const metaType = (orderMetadata?.['orderType'] || '').toLowerCase();
if (metaType === 'membership') return OrderItemCategory.Membership;
// …then, only if no metadata matched:
if (desc.includes('video library') || prod.includes('video_library')) {
  return OrderItemCategory.VideoLibrary;
}
The text matching is a legacy bridge, not the design

Orders created by this app always carry orderType and take the first branch. The description heuristics exist for orders imported from elsewhere — historically Squarespace — where no metadata was ever set. When adding a product, set the metadata: relying on the product name puts the fulfillment behaviour at the mercy of a copy edit.

What fulfillment writes

CategoryEffect on the member
MembershipExtends currentMembershipExpires (or sets Life), assigns a memberId if the member has none, and records the subscription for auto-renewal. A spouse lifetime purchase provisions the second member too.
InstructorLicenseExtends the instructor licence expiry.
SchoolLicenseExtends the school's licence expiry.
VideoLibraryGrants or extends the Class Video Library subscription.
VodCreates a VideoGrant for a single title.
GradingCreates the grading record — or marks an existing unpaid one paid. Duplicate protection queries for a grading already created from this order.
Event, OtherRecorded only; no automatic entitlement.

Every change lands on the member document, and Cloud Function triggers then propagate the expiry dates into /acl/{email} — which is what the Storage rules read to decide whether a member may download tiered resources. Fulfillment is therefore the step that actually grants access, not just the step that records a sale.

Grading payments that cannot be honoured

Two cases are refused rather than applied: paying for a level already achieved, and paying for a level already paid for. The grading is still created and flagged for review, and both the student and the admins are notified with an explanation. See docs/gradings.md.

Order records

Every processed payment is written twice: canonically to /orders/{orderId} (admin-only), and mirrored into /members/{memberDocId}/orders/{orderDocId} so a member can read their own history without being able to read anyone else's. Both are written with the Admin SDK; the rules forbid all client writes to either.

Troubleshooting & Known Gotchas

⚠️ Backups: "Permission 'iam.serviceAccounts.signBlob' denied"

When calling listBackups, the Cloud Function requires the Service Account Token Creator (roles/iam.serviceAccountTokenCreator) IAM role to generate signed GCS download URLs.

ℹ️ Email Case Normalization

All login and member lookup queries normalize emails to lowercase (email.toLowerCase().trim()). Firestore /acl/{email} document IDs must always be stored in lowercase.
